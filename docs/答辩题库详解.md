## A. 项目与架构

### Q1. 用一句话介绍这个项目

**一句话**：面向在校学生的读书笔记社区，支持私有/公开笔记、审核、点赞评论关注，AI 只做辅助、结果需人工确认。

**详解**：

1. **背景**：学生读书笔记散落在纸本、备忘录、截图里，复习时找不到，也缺少交流和自测手段。
2. **方案**：把"书 + 笔记正文 + 书页截图"放在一起，支持公开分享；公开内容经过审核后进入社区流，可被点赞、评论、关注。
3. **AI 定位**：提供总结、适宜人群、评分和客服，但**不直接改笔记**，用户点"保存"才写入，一篇笔记只留一条 AI 结果。
4. **规模**：后端 64 个 Java 文件、10 张表、42 个接口；前端 Vue 3 共 11 个页面；接口测试 56 个用例全通过。

**项目落点**：`README.md` 功能清单、`docs/screenshots/` 截图。

**追问**：和普通笔记 App 的区别？→ 社区 + 审核 + AI 辅助三位一体，且强调"辅助思考而非代替思考"。

### Q2. 为什么这样分层？Controller/Service/Mapper 各做什么？

**一句话**：Controller 管进出、Service 管规则、Mapper 管 SQL，改规则只动一处。

**详解**：

1. **Controller（接口层）**：接收 HTTP 参数、`@Valid` 校验、调用 Service、用 `Result` 包装响应；**不写业务判断**。例：`NoteController.create` 只做 `@Valid` + 调 Service。
2. **Service（业务层）**：业务规则（谁能改、什么状态能点赞）、权限校验、事务边界、跨表组装。例：`NoteService.create` 决定 `status=2`。
3. **Mapper（数据层）**：只做 CRUD 与查询，不写 if/else 业务。例：`NoteMapper extends BaseMapper<Note>`。
4. **收益**：审核规则只存在 `NoteService` 一处；换接口协议（HTTP→RPC）不影响业务；Service 可被定时任务、消息消费者复用。
5. **反例**：Controller 直接写 SQL、Service 拼 JSON——最后没人说得清规则在哪。

**项目落点**：`src/main/java/com/noteworkshop/note/NoteController.java`、`NoteService.java:42`。

**追问**：Service 之间能互相调用吗？→ 可以（如 `AdminService` 调 `CommentService.adminDelete`），但要避免循环依赖；本项目通过拆分职责避免。

### Q3. 为什么按业务垂直分包，而不是 controller/service/mapper 三大包？

**一句话**：按业务切，一个功能的所有代码在一起，改动收敛、讲解清晰。

**详解**：

1. **结构**：`user/ note/ comment/ follow/ admin/ ai/ file/`，每个包内自带 Controller、Service、Mapper、DTO。
2. **好处**：加"收藏"功能只动 `favorite/` 一个包；定位问题按业务找；未来拆微服务时边界天然清晰。
3. **代价**：跨包公共能力要抽到 `common/`（Result、异常、分页），否则重复。
4. **对比**：三大包适合小项目或纯 CRUD；业务一多，`service` 包会变成几十个类的大杂烩。
5. **答辩说法**：这是"模块化单体"的组织方式，既保留单体部署的简单，又接近微服务的边界。

**项目落点**：`src/main/java/com/noteworkshop/` 下 10 个业务包。

**追问**：公共实体放哪？→ 本项目没有跨模块共享实体；若需要，放 `common/domain` 并禁止反向依赖。

### Q4. 一个请求从浏览器到数据库经历了什么？

**一句话**：axios 加 token → 代理 → Tomcat → 拦截器 → Controller → Service → Mapper → MySQL → JSON → 前端解包。

**详解**：

1. **前端**：`frontend/src/api/index.js:23` 请求拦截器加 `Authorization: Bearer <token>`。
2. **代理**：开发态 `/api` 由 `vue.config.js` 转发到 8080；生产态同源。
3. **容器**：Tomcat 交给 `DispatcherServlet`，按路径找到 Controller。
4. **拦截器**：`AuthInterceptor` 验 token 并写 `UserContext`；`/api/admin/**` 再走 `AdminInterceptor` 查角色。
5. **Controller**：`@Valid` 校验参数（失败由全局处理器返回 400）。
6. **Service**：业务规则、权限、`@Transactional`。
7. **Mapper/MySQL**：MyBatis-Plus 生成 SQL，分页插件拼 `LIMIT`。
8. **返回**：对象由 Jackson 序列化成 JSON；异常由 `@RestControllerAdvice` 统一兜底。
9. **前端**：响应拦截器判断 `code`，0 就返回 `data`，401 清 token 跳登录。

**项目落点**：`WebMvcConfig.java:30`、`AuthInterceptor.java:17`、`api/index.js:35`。

**追问**：异常在哪一层被吃掉？→ 全局异常处理器；Controller 不写 try/catch。

### Q5. 项目的统一响应和异常是怎么设计的？

**一句话**：所有接口返回 `Result{code,message,data}`，业务异常用 `BizException` 带码抛出，全局处理器统一转换。

**详解**：

1. **成功**：`Result.ok(data)` → `{"code":0,"message":"ok","data":...}`。
2. **业务异常**：`throw new BizException(403,"无权操作他人的笔记")`，由 `@ExceptionHandler(BizException.class)` 转成 `code=403`。
3. **参数校验**：`MethodArgumentNotValidException` → 取第一个字段错误信息，返回 400。
4. **上传超限**：`MaxUploadSizeExceededException` → 400 "文件过大"。
5. **静态资源 404**：`NoResourceFoundException` → 404 "资源不存在"（否则会被兜底成 500）。
6. **未知异常**：记录 error 日志，返回 500 "系统繁忙"，**不把堆栈返回给前端**。
7. **为什么业务码放 body**：前端统一解包、统一提示；代价是不符合严格 REST 语义，需要监控 body。

**项目落点**：`common/Result.java`、`common/BizException.java`、`common/GlobalExceptionHandler.java`。

**追问**：为什么不用 HTTP 状态码？→ 可以，但前后端要统一；本项目选择 body code，团队约定成本更低。

### Q6. 项目里你觉得设计得最好的地方是？

**一句话**：审核状态机由服务端强制 + 点赞用唯一索引和原子计数，简单但很难被绕过。

**详解**：

1. **状态机在服务端**：`NoteService.create/update` 里 `status` 永远由后端计算，前端传 `isPublic=1` 也只能进待审核；公开列表只查 `is_public=1 AND status=1`。
2. **为什么好**：审核是平台的核心规则，放在客户端就不叫规则；而且修改后自动回到待审核，避免"先过审再改内容"。
3. **点赞幂等**：`note_like` 唯一索引 + 先查后改 + `like_count = like_count ± 1`，不重复、不丢更新。
4. **为什么好**：没有引入 Redis/分布式锁，两个简单机制解决 90% 场景，符合"先用最简单方案"的工程原则。
5. **可讲的第三个**：评论级联删除用 BFS + 一条批量 UPDATE；AI 失败降级 + 日志统计。

**项目落点**：`NoteService.java:42-73`、`NoteService.java:145-178`。

**追问**：这些方案有什么局限？→ 点赞计数仍是弱一致；状态机没有用状态模式，规则多了会膨胀（见 Q45/H2）。

## B. 鉴权与安全

### Q7. JWT 的结构是什么？你的 token 里放了什么？

**一句话**：三段 Base64Url——头、载荷、签名；载荷放 userId、username、签发/过期时间，绝不放密码。

**详解**：

1. **header**：`{"alg":"HS384"}`，声明签名算法。
2. **payload**：`sub`（用户 id）、`username`、`iat`（签发时间）、`exp`（过期时间）。**只是 Base64Url 编码，任何人都能解开看**。
3. **signature**：用服务端密钥对 `header.payload` 做 HMAC，防篡改；密钥泄露等于所有人可伪造。
4. **为什么放 userId 而不是整份用户信息**：token 越小越好（每次请求都带），用户资料可变，放 id 每次查库最准。
5. **为什么不能放密码/手机号**：payload 可解码，等于明文传输。

**项目落点**：`security/JwtUtil.java:25-34`（签发）、`:36-42`（验签）。

**追问**：token 被改一个字符会怎样？→ 签名校验失败，`parse` 抛异常，拦截器返回 401。

### Q8. 为什么用 HS384？密钥怎么管理？

**一句话**：算法由密钥长度自动决定（51 字节 → HS384）；密钥用环境变量注入，生产必须替换。

**详解**：

1. **HS 是什么**：HMAC + SHA，对称算法，签名和验签用同一个密钥，适合单体/内部服务。
2. **为什么是 384**：`Keys.hmacShaKeyFor` 要求至少 256 位；密钥 51 字节 = 408 位，jjwt 选择 HS384。
3. **和 RS256 的区别**：RS256 非对称，私钥签名、公钥验签，适合多服务/第三方验签；HS 更简单更快。
4. **密钥管理**：`JWT_SECRET` 环境变量覆盖，配置文件里的值只是开发默认；生产要求 ≥32 字节、定期轮换。
5. **轮换怎么做**：支持多密钥（kid），新 token 用新密钥，旧 token 在过期前仍可用旧密钥验。

**项目落点**：`application.yml` 的 `app.jwt.secret`、`config/JwtProperties.java`。

**追问**：密钥写配置文件有什么风险？→ 提交仓库即泄露；本项目支持环境变量，并在 README 标注生产必须替换。

### Q9. JWT 和 Session 的区别？为什么选 JWT？

**一句话**：Session 把状态放服务端，JWT 把状态放客户端；前者好注销，后者好扩展。

**详解**：

1. **Session**：登录后服务端存 session，客户端只拿 sessionId（Cookie）；每次请求查存储。
2. **JWT**：用户信息签在 token 里，服务端验签即可，不存会话。
3. **扩展性**：多台后端时 Session 要共享（Redis/粘性会话）；JWT 天然无状态，加机器即可。
4. **注销**：Session 删记录就失效；JWT 到期前一直有效，需要黑名单/短过期。
5. **本项目选择**：前后端分离、演示环境单机，JWT 更简单；代价是无法主动踢人（见 Q10）。

**项目落点**：`security/JwtUtil.java`、`security/AuthInterceptor.java`。

**追问**：JWT 一定比 Session 好吗？→ 不一定；后台管理系统更看重可控性，Session/集中式 token 也常见。

### Q10. JWT 怎么注销？token 泄露怎么办？

**一句话**：当前只能前端删 token；生产要加 Redis 黑名单或短 token + refresh token。

**详解**：

1. **现状**：前端清 localStorage，服务端无感知——旧 token 在 7 天内仍可用。
2. **风险**：token 被盗后无法主动失效；用户改密码后旧 token 依然有效。
3. **方案 A（黑名单）**：token 里加 `jti`，注销时把 jti 写入 Redis 并设过期时间；拦截器先查黑名单。改动小、可控。
4. **方案 B（短 token + 刷新）**：access token 15 分钟，refresh token 7 天且可撤销；泄露窗口小。
5. **方案 C（改密码失效）**：用户表存 `token_version`，签进 token，改密码时 +1，验签后比对。
6. **存储安全**：Cookie 用 `HttpOnly + Secure + SameSite`；localStorage 要防 XSS；全程 HTTPS。

**项目落点**：`JwtUtil.issue`（可加 jti）、`UserService.login`。

**追问**：现在为什么不做？→ 面试项目范围控制；加 Redis 会增加部署复杂度，已在"不足"里主动说明。

### Q11. 为什么用拦截器而不是 Spring Security？

**一句话**：权限模型只有"登录 + 管理员"两级，拦截器 + 路径匹配足够，代码直观；Spring Security 更全但更重。

**详解**：

1. **拦截器能做什么**：`preHandle` 拿 request、抛业务异常、写 ThreadLocal；`afterCompletion` 清理。
2. **本项目实现**：`AuthInterceptor` 拦 `/api/**` 排除登录/公开接口；`AdminInterceptor` 拦 `/api/admin/**`。
3. **Security 的优势**：认证方式多（表单、OAuth2、JWT 资源服务器）、方法级注解、CSRF、会话固定防护、生态成熟。
4. **Security 的成本**：过滤器链、默认登录页、配置类，初学容易"配了但不知道发生了什么"。
5. **迁移路径**：若要做第三方登录/细粒度 RBAC，换成 Security + JWT Filter，业务代码基本不动（因为权限判断在 Service）。

**项目落点**：`config/WebMvcConfig.java:30`、`security/AuthInterceptor.java`、`security/AdminInterceptor.java`。

**追问**：拦截器能替代 Security 吗？→ 小项目可以；涉及 OAuth2、方法级权限、CSRF 时建议用 Security。

### Q12. 401 和 403 的区别？你的代码哪里返回？

**一句话**：401 是"没证明你是谁"，403 是"证明了但不让你干"。

**详解**：

1. **401 Unauthorized**：没带 token、token 篡改、token 过期。`AuthInterceptor.java:24`、`:30`。
2. **403 Forbidden**：已登录但无权限。项目里有三处：
   - 改/删别人的笔记：`NoteService.requireOwned` 抛 403；
   - 非管理员进后台：`AdminInterceptor` 抛 403；
   - 访问别人的 AI 会话：`AiService.requireSession` 抛 403。
3. **业务码**：本项目把 401/403 放在 body 的 `code`，HTTP 仍是 200；前端拦截器按 `code` 处理。
4. **前端行为**：401 清 token 跳登录；403 只提示"无权限"，不跳登录。
5. **易错**：把 403 也当 401 处理，会导致用户被反复踢回登录页。

**项目落点**：`AuthInterceptor.java:22-31`、`NoteService.java:200-208`、`AdminInterceptor.java:22-25`。

**追问**：未登录访问管理员接口返回什么？→ 先被 Auth 拦，401；登录了但不是管理员，才 403。

### Q13. 如何防止用户改别人的笔记/评论？

**一句话**：Service 层用当前登录用户与资源归属比对，前端传的 userId 一律不信。

**详解**：

1. **来源可信**：`userId` 只从 JWT 解析（`UserContext.require()`），不读请求体里的 userId。
2. **笔记**：`requireOwned(userId, noteId)` 查库比对 `note.userId`，不一致 403。
3. **评论**：删除前校验 `comment.userId == 当前用户`（`CommentService.delete`）。
4. **AI 会话**：`requireSession` 校验 `session.userId`。
5. **水平 vs 垂直**：水平是同角色互相越权（改别人笔记）；垂直是低角色干高角色的事（普通用户进后台），由 `AdminInterceptor` 防。
6. **测试证据**：`api-test.mjs` 有"非作者不能编辑他人笔记"用例，返回 403。

**项目落点**：`NoteService.java:200`、`CommentService.java:103-113`、`AiService.java:189-198`。

**追问**：前端按钮隐藏了还需要后端校验吗？→ 必须；直接调接口就绕过了。

### Q14. BCrypt 为什么比 MD5 安全？

**一句话**：BCrypt 自带随机盐、故意算得慢，MD5 又快又无盐，撞库成本极低。

**详解**：

1. **加盐**：每个密码生成随机盐并存在哈希串里，同样密码每次结果不同，彩虹表失效。
2. **慢**：cost=10 表示 2^10 次迭代，单次几十毫秒；攻击者每秒只能试很少的密码。
3. **可调**：硬件变快就调高 cost，旧哈希仍可校验（`matches` 会读哈希里的 cost）。
4. **MD5 的问题**：无盐、速度极快、已被证明可构造碰撞；数据库泄露后可批量撞库。
5. **本项目**：注册 `encode`、登录 `matches`，数据库存 60 字符的 BCrypt 串，日志与响应都不返回密码。

**项目落点**：`UserService.register/login`、`user` 表 `password VARCHAR(100)`。

**追问**：BCrypt 能解密吗？→ 不能，也不需要；校验是重新计算比对。

### Q15. 文件上传做了哪些安全校验？

**一句话**：非空 + 后缀白名单 + 大小限制 + UUID 重命名 + 只存相对 URL；生产再加文件头校验与对象存储。

**详解**：

1. **非空**：`file == null || file.isEmpty()` 直接拒绝。
2. **后缀白名单**：只允许 jpg/jpeg/png/gif/webp，防止上传 `.jsp/.php/.exe`。
3. **大小**：Spring 配置单文件 10MB、请求 50MB；超限由全局处理器返回 400。
4. **重命名**：UUID + 原后缀，防覆盖、防路径穿越（`../../`）。
5. **存储**：只存 `/uploads/xxx.png` 相对路径，数据库不存磁盘绝对路径，换存储不用改数据。
6. **生产加强**：读文件头（magic number）确认真实类型、图片压缩去 EXIF、接杀毒、存 OSS 并限制访问。

**项目落点**：`file/FileStorageService.java`、`config/WebMvcConfig.java:56`（静态映射）。

**追问**：只校验后缀够吗？→ 不够，攻击者可伪造后缀；要读文件头或交给图片处理库解码验证。

### Q17. 为什么 note 要同时有 is_public 和 status？

**一句话**：一个表示用户想不想公开，一个表示平台让不让公开，职责不同。

**详解**：

1. **is_public**：用户意愿（0 私有、1 公开），由用户控制。
2. **status**：平台审核状态（1 正常、2 待审核、3 驳回、0 下架），由管理员控制。
3. **可见规则**：`is_public=1 AND status=1` 才对所有人可见；作者本人可看自己的全部。
4. **为什么不用一个字段**：合并后无法表达"用户想公开但被驳回""用户设私有但被下架"等组合，也没法做审核队列。
5. **数据查询**：公开列表固定带这两个条件，索引 `(is_public,status,like_count)` 正好覆盖。

**项目落点**：`sql/schema.sql` 的 `note` 表、`NoteService.java:90-101`。

**追问**：私有笔记需要审核吗？→ 不需要，`status=1` 直接可看（仅自己）。

### Q18. 为什么要冗余 like_count？不会不一致吗？

**一句话**：为了列表展示和排序不扫全表；写入用原子 SQL 保证不丢更新，极端场景再校准。

**详解**：

1. **读多写少**：首页每篇笔记都要显示点赞数、还要按点赞排序，`count(*)` 每次扫 `note_like` 太贵。
2. **写入**：`UPDATE note SET like_count = like_count + 1` 由数据库保证原子性，并发不会丢更新。
3. **不一致场景**：点赞记录写入成功但计数更新失败（事务回滚可避免）；历史脏数据；手动改库。
4. **校准**：定时任务 `UPDATE note n SET like_count=(SELECT count(*) FROM note_like l WHERE l.note_id=n.id)`。
5. **更强方案**：Redis 计数 + 异步落库；或 `INSERT ... ON DUPLICATE KEY UPDATE` 配合触发器。

**项目落点**：`NoteService.java:162-173`。

**追问**：为什么不用数据库触发器？→ 触发器难调试、难迁移，业务层显式更可控。

### Q19. 建了哪些索引？分别服务什么查询？

**一句话**：五个关键索引，全部按"最左前缀 + 实际查询"设计。

**详解**：

| 索引 | 服务的 SQL |
| --- | --- |
| `note(is_public,status,like_count)` | 公开流 `WHERE is_public=1 AND status=1 ORDER BY like_count DESC` |
| `note_like(user_id,note_id)` 唯一 | 是否点过、我的点赞、防重复 |
| `comment(note_id,deleted)` | 某篇笔记的评论列表 |
| `follow(follower_id,followee_id)` 唯一 | 关注关系、防重复、粉丝统计 |
| `note_ai(note_id)` 唯一 | 一篇笔记只留一条 AI 结果 |

1. **最左前缀**：联合索引必须从第一列开始用；只查 `like_count` 用不上 `(is_public,status,like_count)`。
2. **唯一索引的双重作用**：约束 + 加速等值查询。
3. **代价**：写入维护索引、占空间；不在低基数列（如 status 单独）乱建。
4. **验证**：`EXPLAIN` 看 `key` 是否命中、`rows` 是否变小。

**项目落点**：`sql/schema.sql`。

**追问**：`status` 只有 4 个值，单独建索引有意义吗？→ 选择性低，通常不单独建；本项目是组合索引的一部分。

### Q20. 为什么用 MyBatis-Plus 而不是 JPA？

**一句话**：SQL 可控、条件构造器和分页插件好用，适合"审核状态、分组统计"这类明确 SQL 的场景。

**详解**：

1. **SQL 可控**：复杂查询（分组排行、状态过滤）直接写 SQL/Wrapper，性能调优直观。
2. **开发效率**：`BaseMapper` 自带 CRUD；`LambdaQueryWrapper` 类型安全；分页插件自动 count + limit。
3. **国内生态**：资料多、团队熟悉；面试项目常见。
4. **JPA 的优势**：对象模型、自动 DDL、跨数据库；复杂查询要 JPQL/Criteria，调优不如 SQL 直接。
5. **选择依据**：本项目查询模式明确、需要精细控制 SQL，选 MyBatis-Plus；若做领域模型复杂、换库频繁，JPA 更合适。

**项目落点**：`pom.xml`、`config/MybatisPlusConfig.java`。

**追问**：MyBatis 的 N+1 怎么避免？→ 批量查（`selectByIds`）+ 内存组装，本项目 `attachAuthors` 就是这么做的。

### Q21. MyBatis-Plus 分页原理？

**一句话**：拦截器改写 SQL，先查总数再拼 `LIMIT`，并限制最大页大小。

**详解**：

1. **入口**：`PaginationInnerInterceptor` 注册在 `MybatisPlusInterceptor`。
2. **流程**：检测到 `Page` 参数 → 执行 `count` SQL → 在原 SQL 后拼 `LIMIT offset,size`。
3. **返回值**：`Page` 里有 `records/total/current/size`，项目转成 `PageResult`。
4. **保护**：`setMaxLimit(100)` 防止 `size=999999` 拖垮数据库。
5. **深分页**：`LIMIT 100000,10` 仍慢，优化用"游标/上次最大 id"（`WHERE id < lastId LIMIT 10`）。

**项目落点**：`config/MybatisPlusConfig.java`、`common/PageResult.java`。

**追问**：count 很慢怎么办？→ 缓存总数、近似计数、或前端改成"加载更多"不显示总数。

### Q22. `@Transactional` 在哪些情况下会失效？

**一句话**：自调用、非 public、异常被吞、非运行时异常、跨线程——五种常见失效。

**详解**：

1. **同类自调用**：`this.methodB()` 不走代理，B 上的事务不生效；解决：拆类或注入自身代理。
2. **非 public**：Spring AOP 默认只代理 public 方法。
3. **异常被吞**：catch 后不抛，事务不会回滚。
4. **默认只回滚 RuntimeException/Error**：受检异常要 `rollbackFor = Exception.class`。
5. **跨线程**：事务绑定在当前线程，子线程不共享。
6. **本项目的反向用法**：`AiService.chat` **故意不加事务**，因为 AI 失败时用户消息和调用日志要保留，否则统计不到失败。

**项目落点**：`NoteService`（加事务）、`AiService.chat`（不加事务的注释）。

**追问**：事务里能调远程接口吗？→ 尽量不要，连接被占用；先落库再异步调用。

## D. 业务设计

### Q23. 讲一下审核状态机。

**一句话**：1 已发布、2 待审核、3 已驳回、0 已下架；公开创建/修改进 2，通过变 1，驳回变 3，下架变 0。

**详解**：

1. **入口**：`NoteService.create`：公开 → 2，私有 → 1。
2. **修改**：`update` 里公开一律重置为 2，并清空驳回原因与审核时间。
3. **通过**：`AdminService.review` 校验当前必须是 2，置 1 并写 `reviewed_at`。
4. **驳回**：置 3，写 `reject_reason`，用户能看到原因。
5. **下架**：管理员置 0，公开接口按可见性规则直接 404。
6. **可见性**：非作者只可见 `is_public=1 AND status=1`；作者可见自己的全部状态。

**项目落点**：`NoteService.java:24-27,42-73`、`AdminService.java:98-112`。

**追问**：为什么修改后要重新审核？→ 防止"先过审再改内容"绕过审核。

### Q24. 用户能不能绕过前端直接调接口把笔记设为公开？

**一句话**：不能，`status` 由服务端强制，客户端只能表达 `is_public` 意愿。

**详解**：

1. **接口入参**：`NoteRequest` 只有 `isPublic`，没有 `status`。
2. **服务端**：`create/update` 里 `status = isPublic ? 2 : 1`，客户端传什么都不影响。
3. **读接口**：公开列表/详情只认 `is_public=1 AND status=1`。
4. **证据**：接口测试"待审核笔记不出现在公开列表"就是防这个。
5. **延伸**：点赞、评论都要求笔记 `status=1`，避免绕过审核互动。

**项目落点**：`NoteService.java:48-50`、`NoteService.java:150-153`。

**追问**：管理员能不能直接把私有笔记设为公开？→ 走审核接口只改 status，不替用户改 is_public；产品上应尊重用户意愿。

### Q25. 驳回后用户修改，为什么又回到待审核？

**一句话**：只要改的是公开笔记，就当作新内容重新排队，避免"带病过审"。

**详解**：

1. **代码**：`update` 里 `status = isPublic ? 2 : 1`，同时 `rejectReason = null`、`reviewedAt = null`。
2. **原因**：审核针对的是"当时的内容"，内容变了就要重审；否则用户可以先提交合规内容过审，再改成违规内容。
3. **体验**：前端会提示"修改后需重新审核"，"我的笔记"显示待审核标签。
4. **私有转公开**：同样进 2；公开转私有则直接 1，不再展示。
5. **代价**：用户频繁改就要频繁审；可加"仅标题/错别字修改不重审"的规则（需内容 diff）。

**项目落点**：`NoteService.java:59-73`。

**追问**：如果只改错别字也要重审吗？→ 目前是；更细的做法是对比正文哈希，只改格式不重审。

### Q26. 点赞怎么保证不重复、计数不出错？

**一句话**：唯一索引防重复，SQL 原子自增防丢更新，取消时 `GREATEST` 防负数。

**详解**：

1. **防重复**：`note_like` 上 `(user_id,note_id)` 唯一；业务先查再决定插入/删除。
2. **原子计数**：`like_count = like_count + 1` 在数据库内完成，两个并发请求不会互相覆盖。
3. **防负数**：取消时 `GREATEST(like_count-1, 0)`。
4. **事务**：删/插记录与更新计数在同一事务，避免"记录没了计数还在"。
5. **残留竞态**：两个请求同时判断"没点过"都插入，第二个被唯一索引拒绝（抛异常）；高并发建议 `INSERT ... ON DUPLICATE KEY UPDATE` 或 Redis 计数。

**项目落点**：`NoteService.java:145-178`、`sql/schema.sql` 的 `note_like`。

**追问**：为什么要返回最新计数？→ 前端本地加减会与实际不一致，以服务端为准。

### Q27. 评论树怎么构建？为什么不用递归查库？

**一句话**：一次查出该笔记所有评论，内存按 parentId 分组挂树，避免 N+1。

**详解**：

1. **存储**：邻接表，`parent_id=0` 为一级评论。
2. **查询**：`WHERE note_id=? AND deleted=0 ORDER BY id`，一次拿全。
3. **组装**：`groupingBy(parentId)` 建邻接表，再遍历挂 `children`；O(n)。
4. **为什么不用递归**：每条评论查一次子节点 = N+1 次 SQL；10 条评论 11 次查询，慢且不可控。
5. **规模上限**：一次读全篇评论，超大评论区要改分页、路径枚举（`/1/5/9`）或闭包表。

**项目落点**：`CommentService.java:36-68`。

**追问**：删除父评论后，子评论的 parentId 还指向它吗？→ 是，靠 `deleted=1` 逻辑删除，树结构不断。

---

### Q28. 父评论删除，子评论怎么处理？为什么逻辑删除？

**一句话**：BFS 收集所有子孙，一条 UPDATE 批量置 deleted=1，并扣减计数；逻辑删除保留审计与回复链。

**详解**：

1. **收集**：查出该笔记未删除评论，建 `parentId → children`，从根 BFS，`Set` 去重防环。
2. **删除**：`UPDATE comment SET deleted=1 WHERE id IN (...)`，一条 SQL。
3. **计数**：`comment_count = GREATEST(comment_count - N, 0)`。
4. **为什么逻辑删除**：可追溯、可恢复、回复关系不断链；物理删除会让"回复的评论不存在"。
5. **代价**：所有查询都要带 `deleted=0`；数据量大时要归档。

**项目落点**：`CommentService.java:125-150`。

**追问**：为什么不用数据库外键 `ON DELETE CASCADE`？→ 那是物理删除，且逻辑删除/分库场景不适用。

### Q29. 热门作者怎么统计？数据量大怎么办？

**一句话**：按 followee_id 分组计数倒序取前 10，再批量查用户；量大用定时任务 + 缓存。

**详解**：

1. **SQL**：`SELECT followee_id, count(*) cnt FROM follow GROUP BY followee_id ORDER BY cnt DESC LIMIT 10`。
2. **避免 N+1**：拿到 10 个 id 后 `selectByIds` 一次查用户，再按原顺序组装。
3. **实时 vs 离线**：关注量大时 `GROUP BY` 全表很慢，改为每小时算一次榜单写缓存。
4. **口径**：只统计公开且已发布笔记的作者，避免给违规账号导流（可扩展）。
5. **缓存**：Redis 存榜单 JSON，设 TTL；关注/取关时不一定立刻刷新。

**项目落点**：`FollowService.hotAuthors`、`GET /api/public/authors/hot`。

**追问**：粉丝数要不要冗余？→ 数据量大可加 `user.fans_count`，关注时 ±1，定时校准。

### Q30. 管理员权限怎么做的？为什么单独一个拦截器？

**一句话**：`AdminInterceptor` 在登录拦截之后执行，查库确认 role=ADMIN，只拦 `/api/admin/**`。

**详解**：

1. **顺序**：`WebMvcConfig` 里 Auth `.order(1)`、Admin `.order(2)`；管理员校验要用 `UserContext`，必须后执行。
2. **查库而非读 token**：token 签发后角色可能被改，查库能立即生效。
3. **职责单一**：认证归 Auth，授权归 Admin；普通接口不受影响。
4. **双重校验**：拦截器挡入口，Service 里再校验业务状态（审核只能对 status=2）。
5. **失败**：未登录先 401；已登录非管理员 403。

**项目落点**：`config/WebMvcConfig.java:30-43`、`security/AdminInterceptor.java`。

**追问**：为什么不把 role 放 token 省一次查询？→ 可以，但角色变更要等 token 过期才生效；管理后台对实时性要求高。

### Q31. 为什么不能禁用管理员账号？审核接口为什么校验状态？

**一句话**：防止把系统锁死；审核只接受待审核，防止重复审核和越权改状态。

**详解**：

1. **禁用管理员**：`AdminService.setUserStatus` 判断目标角色是 ADMIN 且要禁用时抛 400；否则可能把所有管理员禁掉，没人能进后台。
2. **审核状态**：`review` 要求 `note.status == 2`；否则已发布的笔记可被直接驳回、下架的笔记可被"审核通过"复活。
3. **幂等**：重复审核同一篇会被拒绝，避免重复写审核记录。
4. **审计**：审核写 `reviewed_at`，配合日志可追溯谁在什么时候审的。
5. **延伸**：生产还应加"操作日志表"，记录管理员 id、动作、目标、时间。

**项目落点**：`AdminService.java:73-84,98-112`。

**追问**：管理员能不能审自己的笔记？→ 当前可以；严格场景应禁止（避免自审自过）。

### Q34. 客服会话怎么隔离？越权怎么处理？

**一句话**：会话带 user_id，每次操作先 `requireSession` 校验归属，不一致 403。

1. **归属字段**：`ai_chat_session.user_id`。
2. **校验**：`requireSession(userId, sessionId)` 查库比对，不同即抛 403。
3. **消息隔离**：消息按 `session_id` 查，天然不会串会话。
4. **列表隔离**：`sessions` 只查当前用户的会话。
5. **跨用户测试**：用 B 的 token 访问 A 的 sessionId，返回 403（接口测试覆盖）。

**项目落点**：`AiService.java:189-198`、`AiController.java`。

### Q35. 为什么只带最近 20 条消息？

**一句话**：控制 token 成本与延迟，10 轮足够客服场景；更长用摘要或检索。

**详解**：

1. **成本**：token 按量计费，历史越长越贵。
2. **延迟**：上下文越长，首字延迟越高。
3. **效果**：客服问题通常短程，10 轮足够；超出部分对回答帮助递减。
4. **实现**：`ORDER BY id DESC LIMIT 20` 再反转，保证时间正序。
5. **更好方案**：滚动摘要（把旧对话压成一段）+ 关键信息表 + 向量检索。

**项目落点**：`AiService.java:127-131`、`AiProperties.windowSize=20`。

**追问**：20 条怎么定？→ 经验值（10 轮）；可按场景配置，监控 token 消耗后调整。

### Q36. 没有 API Key 怎么演示？失败会怎样？

**一句话**：演示降级路径——503、日志、统计；主流程不受影响，并说明配 Key 即可真实调用。

**详解**：

1. **调用链**：`callAi` 抛异常 → 写 `ai_call_log`（scene、success=0、latency、error）→ 抛 503。
2. **前端**：提示"AI 未配置/暂不可用"，页面不白屏。
3. **后台**：AI 统计能看到失败次数与场景分布。
4. **演示话术**："没有配置 Key，所以展示的是降级；配置后同一接口会返回总结内容。"
5. **可选**：现场配一个 Key 走通真实调用（注意不要投屏泄露 Key）。

**项目落点**：`AiService.java:59-78,239-250`、`AdminService.aiStats`。

**追问**：为什么失败也要写库？→ 统计与排障；否则不知道是 Key 错、网络错还是限流。

### Q37. 怎么防止客服回答平台无关问题？prompt 注入怎么办？

**一句话**：system prompt 限定范围 + 输入长度限制；生产再加输出审核与工具白名单，不能只靠 prompt。

**详解**：

1. **范围限定**：system prompt 明确"只回答平台使用、读书笔记相关问题，无关问题礼貌拒绝"。
2. **输入约束**：单条消息 ≤2000 字，减少注入空间。
3. **注入风险**：用户说"忽略以上指令"可能让模型越界；prompt 只能降低概率，不能根治。
4. **工程手段**：输出敏感词过滤、返回内容审核、工具调用白名单、按用户限流、人工抽检。
5. **更严场景**：意图分类先挡一层（只放行平台相关意图），再进大模型。

**项目落点**：`application.yml` 的 `app.ai.system-prompt`、`ChatRequest` 的长度校验。

**追问**：如果用户问"帮我写作业"？→ 礼貌拒绝并引导回读书笔记话题。

### Q38. AI 调用很慢，怎么优化？

**一句话**：流式输出 + 超时重试 + 限制 max_tokens + 异步化 + 限流。

**详解**：

1. **流式（SSE）**：首字更快，用户感知好；Spring AI 支持 streaming。
2. **超时/重试**：设置连接与读取超时，失败有限重试（幂等场景）。
3. **限制输出**：`max_tokens`、明确的字数约束，减少生成时间。
4. **异步**：长任务转后台 + 轮询/推送，避免 HTTP 连接长时间占用。
5. **限流**：按用户/接口限流，防单用户打满配额。
6. **降级**：失败快速返回 503，不拖垮线程池。

**项目落点**：`AiService.callAi`、`AiService.chat`。

**追问**：流式怎么实现？→ 后端返回 `text/event-stream`，前端用 `EventSource`/fetch 逐块渲染。

## F. 前端

### Q39. 前端怎么处理登录态？

**一句话**：token 与用户信息存 localStorage，axios 统一加头，401 清空并跳登录。

**详解**：

1. **存储**：`nw_token`、`nw_user`；刷新页面仍在。
2. **全局状态**：`store/auth.js` 用 `reactive`，组件共享登录态。
3. **请求**：`api/index.js:23` 请求拦截器读 token 加 `Authorization`。
4. **响应**：`code=401` 时清 token、跳 `/login`，并用标志位防重复跳转。
5. **安全**：localStorage 有 XSS 风险；更严场景用 HttpOnly Cookie + CSRF 防护。

**项目落点**：`frontend/src/store/auth.js`、`frontend/src/api/index.js`。

**追问**：多标签页登录态不同步？→ 可监听 `storage` 事件同步；当前刷新即可。

### Q40. 路由守卫做了什么？

**一句话**：进入页面前检查 meta：需要登录、需要管理员、仅游客，分别处理。

**详解**：

1. **requiresAuth**：未登录跳 `/login` 并带 `redirect`，登录后跳回。
2. **admin**：非管理员提示并回首页。
3. **guestOnly**：已登录再访问登录/注册页，直接回首页。
4. **标题**：`beforeEach` 里顺手设置 `document.title`。
5. **边界**：前端守卫只提升体验，真正权限在后端；直接调接口仍会被拦。

**项目落点**：`frontend/src/router/index.js:89-106`。

**追问**：守卫里能发请求吗？→ 能但要避免阻塞；需要用户信息时在应用启动时 `bootstrap` 一次。

### Q41. 跨域怎么解决的？生产环境呢？

**一句话**：开发用 devServer 代理，后端配 CORS 放行 8081；生产同源，不需要跨域。

**详解**：

1. **开发**：`vue.config.js` 把 `/api`、`/uploads` 代理到 `http://127.0.0.1:8080`，浏览器视为同源。
2. **CORS**：`WebMvcConfig.addCorsMappings` 只放行 `localhost:8081`、`127.0.0.1:8081`。
3. **预检**：浏览器先发 `OPTIONS`；`AuthInterceptor` 第一行放行，否则预检被拦成 500（实际踩过）。
4. **生产**：前端打包进后端 `static`，同源，无跨域；CORS 配置保留给独立部署场景。
5. **为什么不 `*`**：带凭证时不能通配；限定来源更安全。

**项目落点**：`frontend/vue.config.js`、`config/WebMvcConfig.java:46-53`、`AuthInterceptor.java:19`。

**追问**：为什么预检会带 500？→ 拦截器抛业务异常但没有对应 handler；放行 OPTIONS 后由 Spring 处理。

### Q42. 打包后刷新 /notes/1 为什么 404？怎么解决？

**一句话**：history 路由在服务器上没有对应文件；用 `SpaForwardController` 把前端路由回退到 index.html。

**详解**：

1. **现象**：从首页点进详情正常，刷新就 404。
2. **原因**：`/notes/1` 是前端路由，Tomcat 找不到该资源。
3. **解决**：`SpaForwardController` 映射 `/notes/**`、`/users/**`、`/ai`、`/admin` 等，`forward:/index.html`。
4. **不影响接口**：`/api/**` 优先匹配 Controller；静态资源（js/css）直接命中。
5. **替代**：改用 hash 路由（`/#/notes/1`）也能避免，但 URL 不美观。

**项目落点**：`config/SpaForwardController.java`。

**追问**：为什么不把所有路径都 forward？→ 会吃掉静态资源与 API 的 404 语义，按前端路由白名单更安全。

## G. 工程化与测试

### Q43. 日志都记了什么？怎么避免泄露密码？

**一句话**：记登录/注册、上传、审核、下架、评论、AI 失败；只记 username/userId，不记密码与 token。

**详解**：

1. **业务日志**：`log.info("用户登录成功 username={} id={}", ...)`、文件上传、审核结果、管理员操作。
2. **异常日志**：AI 失败 `log.warn` 带 sessionId；未知异常 `log.error` 带堆栈（服务端可见，不返回前端）。
3. **脱敏**：不打印 password、Authorization、完整手机号；DTO 的 `@JsonIgnore` 保证密码不出现在响应。
4. **级别**：生产 info，排查时开 debug；SQL 日志只在开发开。
5. **落盘**：Logback 默认控制台；生产配滚动文件 + 保留天数。

**项目落点**：`UserService`、`FileStorageService`、`AdminService`、`AiService` 的 `@Slf4j`。

**追问**：日志里出现 token 有什么风险？→ 拿到即可冒充用户；必须脱敏。

### Q44. 56 个接口用例覆盖了哪些风险？

**一句话**：认证、越权、审核流、幂等、级联、后台权限、AI 降级、404。

**详解**：

1. **认证**：未登录 401、篡改 token 401、普通用户进后台 403。
2. **参数**：密码过短 400、重复注册 400。
3. **上传**：图片成功、非图片 400、静态访问 200。
4. **笔记**：待审核不进公开流、作者可见、他人编辑 403、驳回原因可见。
5. **互动**：点赞/取消/列表、评论二级回复、删父级联删子。
6. **关注**：关注/取关、粉丝数、热门榜、不能关注自己。
7. **后台**：禁用用户后登录 403、按状态筛选、删违规评论、下架后公开 404。
8. **AI**：状态接口、无 Key 时 503、结果保存与详情回显。
9. **缺口**：没有单元测试；并发只做了脚本验证，没进 CI。

**项目落点**：`scripts/api-test.mjs`、`docs/api-test-report.md`。

**追问**：测试怎么跑的？→ Node 22 原生 fetch 直接打真实服务，断言 body 的 `code`。

### Q45. 如果 QPS 涨 100 倍，你怎么改？

**一句话**：先测瓶颈，再按"缓存 → 数据库 → 异步 → 限流 → 扩容"顺序改。

**详解**：

1. **定位**：压测看 RT/错误率；慢 SQL（`EXPLAIN`）、连接池等待、GC、热点接口。
2. **缓存**：公开流、热门榜、作者主页上 Redis；缓存穿透用空值/布隆过滤器。
3. **数据库**：索引优化、读写分离、计数异步化、深分页改游标、归档历史数据。
4. **异步**：AI 调用、通知、图片处理走队列；接口只做快速返回。
5. **限流降级**：网关/接口级限流，AI 与导出等重接口单独配额。
6. **扩容**：服务无状态（JWT 友好）可水平扩；静态资源 CDN；数据库分库分表是最后手段。
7. **一致性**：缓存与库的更新顺序、延迟双删；计数最终一致可接受。

**项目落点**：`MybatisPlusConfig`（分页上限）、`NoteService`（计数）、`AiService`（重接口）。

**追问**：先加缓存还是先加机器？→ 先定位瓶颈；盲加机器可能只是把压力转移到数据库。

## H. 开放题

### H1. 现场加一个"收藏"功能，你怎么设计？

**一句话**：一张中间表 + 唯一索引 + 4 个接口 + 前端入口 + 用例，30 分钟能跑通。

**详解**：

1. **表**：`note_favorite(id,user_id,note_id,created_at)`，唯一索引 `(user_id,note_id)`，索引 `note_id`。
2. **接口**：`POST /api/notes/{id}/favorite`（收藏/取消，返回状态与总数）、`GET /api/notes/favorites`（分页）、详情返回 `favorited`、可选 `GET /api/notes/{id}/favorite/count`。
3. **Service**：校验笔记公开且已发布；先查再插/删；计数可选（同点赞，用原子 SQL）。
4. **前端**：详情页收藏按钮 + "我的收藏"页 + 路由 + 导航入口。
5. **测试**：重复收藏、取消、列表、未登录 401、私有笔记 400。
6. **注意**：收藏与点赞类似但独立；不要把 `like_count` 复用。

**项目落点**：仿 `note_like` 与 `NoteService.toggleLike` 实现。

**追问**：收藏需要审核吗？→ 收藏是私人行为，不需要；但只能收藏已发布公开笔记。

### H2. 你觉得项目最大的不足是什么？

**一句话**：没有单元测试、JWT 无法主动失效、计数弱一致、文件本地存储、AI 同步无限流。

**详解**：

1. **测试**：只有集成脚本，没有 Service 单测；重构时回归成本高。→ JUnit + Mockito 补核心规则。
2. **JWT 注销**：旧 token 到期前一直有效。→ Redis 黑名单 / 短 token + refresh。
3. **计数一致性**：点赞/评论计数冗余，极端并发或故障会偏。→ 定时校准 + 异步计数。
4. **文件**：本地磁盘，扩容/迁移麻烦。→ OSS + CDN，库里只存 key。
5. **AI**：同步调用、无流式、无限流。→ SSE + 超时重试 + 配额。
6. **安全**：无限流、无验证码、无操作审计表。→ 网关限流 + 审计日志。

**项目落点**：`docs/项目代码解析.md` 第七节。

**追问**：为什么先补单测？→ 规则集中在 Service，单测投入产出比最高。

### H3. 如果重做一次，你会改变什么？

**一句话**：接口先行、测试先行、缓存与密钥治理提前设计。

**详解**：

1. **API First**：先写 OpenAPI 再写代码，前后端并行，减少联调返工。
2. **测试**：先写核心 Service 单测（状态机、权限、计数），再接接口。
3. **可观测**：一开始就加 traceId、结构化日志、关键指标。
4. **安全**：密钥全部环境变量、接口限流、操作审计表。
5. **数据**：计数与缓存策略提前定，避免后期补丁。
6. **前端**：组件与请求层先抽象，避免页面里堆逻辑。

**项目落点**：本项目已补 `docs/openapi.yaml` 与测试脚本，算是部分实践。

**追问**：为什么不现在就重做？→ 成本收益；先把不足写清楚，按优先级迭代。

### H5. 你从这个项目学到了什么？

**一句话**：分层与边界、状态机思维、并发下的幂等、AI 工程的降级与成本、测试驱动的联调。

**详解**：

1. **分层**：业务规则集中在 Service，接口层只做转换，改需求时心里有地图。
2. **状态机**：用有限状态描述业务，比一堆 if/else 可维护；状态转换必须服务端强制。
3. **并发**：唯一索引 + 原子更新是最便宜的幂等方案；不要一上来就分布式锁。
4. **AI 工程**：模型会失败、会慢、会贵；要降级、要日志、要限流、要人工确认。
5. **测试**：真实 HTTP 用例能发现"待审核泄露到公开流"这种逻辑漏洞。
6. **表达**：能把技术决策讲成"问题—方案—取舍"，比堆术语更有说服力。

**项目落点**：`docs/项目代码解析.md`、`docs/api-test-report.md`。

**追问**：如果重来，哪个认知变化最大？→ 从"实现功能"转向"设计边界与失败路径"。
