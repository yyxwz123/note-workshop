## A. 项目与架构（Q1–Q6）

### Q1. 用一句话介绍这个项目
**要点**：面向在校学生的读书笔记社区；用户记录私有/公开笔记，公开笔记需审核，支持点赞评论关注；AI 做总结/人群/评分与客服，只辅助不代写。
**追问**：解决什么痛点？→ 笔记零散、缺少复盘、缺少交流与自测。

### Q2. 为什么这样分层？Controller/Service/Mapper 各做什么？
**要点**：
- Controller：接参、`@Valid` 校验、调 Service、包 `Result`，不写业务；
- Service：业务规则、权限、事务、组装；
- Mapper：只做 CRUD，不写业务判断。
**加分**：分层让"审核规则"只存在 Service 一处，改规则不影响接口层。

### Q3. 为什么按业务垂直分包，而不是 controller/service/mapper 三大包？
**要点**：业务边界清晰、改动收敛、便于按模块讲解与拆分；代价是跨包公共代码要靠 `common`。

### Q4. 一个请求从浏览器到数据库经历了什么？
**要点**：axios（加 token）→ dev 代理 → Tomcat/DispatcherServlet → AuthInterceptor → Controller（参数校验）→ Service（事务/权限）→ Mapper → MySQL → `Result` → axios 响应拦截器解包。
**加分**：异常统一由 `@RestControllerAdvice` 兜底。

### Q5. 项目的统一响应和异常是怎么设计的？
**要点**：`Result{code,message,data}`，`code=0` 成功；`BizException` 携带业务码（400/401/403/404/503）；全局处理器分别处理参数校验、上传超限、静态资源 404、未知异常（500 且不泄露堆栈）。

### Q6. 项目里你觉得设计得最好的地方是？
**要点**（任选 2 个）：
- 审核状态机由服务端强制，前端无法绕过；
- 点赞唯一索引 + 原子计数，简单可靠；
- 评论级联删除 BFS 一次批量更新；
- AI 失败降级 + 日志统计，不拖垮主流程。

## B. 鉴权与安全（Q7–Q15）

### Q7. JWT 的结构是什么？你的 token 里放了什么？
**要点**：header.payload.signature 三段 Base64Url；payload 放 `sub=userId`、`username`、`iat`、`exp`；**不放密码等敏感信息**，因为 payload 可解码，安全靠签名。

### Q8. 为什么用 HS384？密钥怎么管理？
**要点**：`signWith(key)` 会根据密钥长度选算法，本项目 51 字节密钥 → HS384；密钥在配置里支持 `JWT_SECRET` 环境变量覆盖，生产必须替换且 ≥32 字节。

### Q9. JWT 和 Session 的区别？为什么选 JWT？
**要点**：JWT 无状态、服务端不存会话、易水平扩展、天然适合前后端分离；Session 需要存储与共享（Redis）。代价是注销困难。

### Q10. JWT 怎么注销？token 泄露怎么办？
**要点**：当前是前端删 token（无服务端失效）。改进：短期 access token + refresh token；Redis 存 jti 黑名单；改密码时使旧 token 失效；HTTPS + HttpOnly 存储（若用 Cookie）。

### Q11. 为什么用拦截器而不是 Spring Security？
**要点**：项目权限模型简单（登录 + 管理员两级），拦截器 + 自定义注解/路径匹配足够，代码直观、易讲清；Spring Security 功能全但配置复杂、默认行为多。真实生产更倾向 Security。

### Q12. 401 和 403 的区别？你的代码哪里返回？
**要点**：401 未认证（没登录/token 失效），拦截器抛；403 已认证但无权限（非作者改笔记、非管理员进后台、越权访问他人会话）。

### Q13. 如何防止用户改别人的笔记/评论？
**要点**：Service 层校验资源归属（`requireOwned`、`comment.userId == currentUserId`、`session.userId == currentUserId`），不依赖前端传的 userId。

### Q14. BCrypt 为什么比 MD5 安全？
**要点**：自带随机盐（防彩虹表）、可调 cost（默认 10，越算越慢防暴力）、同一密码每次哈希不同；MD5 快且可撞库。

### Q15. 文件上传做了哪些安全校验？
**要点**：非空、后缀白名单（jpg/jpeg/png/gif/webp）、大小限制（单文件 10MB）、UUID 重命名防路径穿越与覆盖、只存相对 URL；生产还应校验文件头、接杀毒/图片压缩、存 OSS。

## C. 数据库与 MyBatis-Plus（Q16–Q22）

### Q16. 画一下核心表关系。
**要点**：user 1-N note；note 1-N note_image；user N-N note（note_like）；note 1-N comment（parent_id 自关联）；user N-N user（follow）；note 1-1 note_ai；AI 会话 1-N 消息。

### Q17. 为什么 note 要同时有 is_public 和 status？
**要点**：`is_public` 是用户意愿，`status` 是平台审核结果；只有 `is_public=1 AND status=1` 才对外可见，二者职责分离，才能支持"提交后被驳回"。

### Q18. 为什么要冗余 like_count？不会不一致吗？
**要点**：列表展示与最热排序避免 `count(*)`；用 SQL 原子自增保证并发安全；极端并发仍有竞态，可改 `INSERT ... ON DUPLICATE KEY` 或 Redis 计数 + 定时校准。

### Q19. 建了哪些索引？分别服务什么查询？
**要点**：
- `note(is_public,status,like_count)`：公开流 + 最热排序；
- `note_like(user_id,note_id)` 唯一：点赞幂等 + 我的点赞；
- `comment(note_id,deleted)`：评论列表；
- `follow(follower_id,followee_id)` 唯一：防重复关注；
- `note_ai(note_id)` 唯一：一篇一条 AI 结果。

### Q20. 为什么用 MyBatis-Plus 而不是 JPA？
**要点**：SQL 可控、分页/条件构造器方便、国内生态与面试项目常见；JPA 更偏对象模型、复杂查询要写 JPQL/原生 SQL。MyBatis 对"审核状态 SQL、分组统计"更直接。

### Q21. MyBatis-Plus 分页原理？
**要点**：`PaginationInnerInterceptor` 拦截 SQL，先查 count 再拼 `LIMIT`；设置 `maxLimit=100` 防止一次拉全表。

### Q22. `@Transactional` 在哪些情况下会失效？
**要点**：同类内部自调用（代理不生效）、非 public 方法、异常被吞、非 RuntimeException 默认不回滚、跨线程。项目里 `AiService.chat` 故意不加事务，保证失败日志能落库。

## D. 业务设计（Q23–Q31）

### Q23. 讲一下审核状态机。
**要点**：1 已发布 / 2 待审核 / 3 已驳回 / 0 已下架；公开创建或修改 → 2；通过 → 1；驳回 → 3 + 原因；下架 → 0；公开列表只查 `is_public=1 AND status=1`。

### Q24. 用户能不能绕过前端直接调接口把笔记设为公开？
**要点**：不能。`is_public` 只表示意愿，`status` 由服务端强制设为 2；公开列表按 status 过滤。

### Q25. 驳回后用户修改，为什么又回到待审核？
**要点**：`update` 里只要公开就重置 status=2 并清空 `reject_reason`，保证"改过就要重新审"。

### Q26. 点赞怎么保证不重复、计数不出错？
**要点**：唯一索引兜底 + 先查后删/插；计数用 `like_count = like_count ± 1`（SQL 原子），取消时 `GREATEST(...,0)` 防负数。

### Q27. 评论树怎么构建？为什么不用递归查库？
**要点**：一次查该笔记全部未删除评论，内存 `groupingBy(parentId)` 组装两级树，避免 N+1；数据量大时可改路径枚举/闭包表。

### Q28. 父评论删除，子评论怎么处理？为什么逻辑删除？
**要点**：BFS 收集所有子孙 id → 一条 `UPDATE ... SET deleted=1 WHERE id IN (...)` → 计数减 N；逻辑删除保留审计痕迹、回复链不断。

### Q29. 热门作者怎么统计？数据量大怎么办？
**要点**：`follow` 按 `followee_id` 分组计数倒序取前 10，再批量查用户（避免 N+1）；量大用定时任务算榜 + Redis 缓存。

### Q30. 管理员权限怎么做的？为什么单独一个拦截器？
**要点**：`AdminInterceptor` 在 Auth 之后执行，查库校验 `role=ADMIN`；叠加在 `/api/admin/**`，与普通登录拦截解耦，职责单一。

### Q31. 为什么不能禁用管理员账号？审核接口为什么校验状态？
**要点**：防误操作把系统锁死；审核只接受 status=2，防止重复审核和越权改状态。

## E. AI 模块（Q32–Q38）

### Q32. AI 功能怎么接入的？
**要点**：Spring AI 的 `ChatClient` 调 OpenAI 兼容接口（默认 DeepSeek），`AI_BASE_URL/AI_MODEL/AI_API_KEY` 环境变量注入；三类 prompt 分别做总结、人群、评分。

### Q33. 为什么 AI 结果不直接写入笔记？
**要点**：产品原则"AI 只辅助、不代写"；用户确认后 `save` 才写 `note_ai`，且 `note_id` 唯一，一篇只留一条，避免污染原文。

### Q34. 客服会话怎么隔离？越权怎么处理？
**要点**：会话有 `user_id`，每次操作 `requireSession` 校验归属，不一致返回 403；消息按 `session_id` 查，天然隔离。

### Q35. 为什么只带最近 20 条消息？
**要点**：控制 token 成本与延迟，避免无限拼接；10 轮足够客服场景；更好方案是历史摘要 + 关键信息提取。

### Q36. 没有 API Key 怎么演示？失败会怎样？
**要点**：未配置时调用失败 → 写 `ai_call_log`（success=0、错误、耗时）→ 返回 503 → 前端提示"AI 未配置"；主流程不受影响，后台还能看到失败统计。

### Q37. 怎么防止客服回答平台无关问题？prompt 注入怎么办？
**要点**：system prompt 限定范围并要求礼貌拒绝；输入做长度限制；生产可加敏感词过滤、输出审核、工具调用白名单，不能只靠 prompt。

### Q38. AI 调用很慢，怎么优化？
**要点**：SSE 流式输出、设置超时与重试、限制 max_tokens、异步化 + 进度提示、失败降级、按用户限流。

## F. 前端（Q39–Q42）

### Q39. 前端怎么处理登录态？
**要点**：登录后 token + user 存 localStorage；`auth` store 用 `reactive` 全局共享；axios 请求拦截器统一加 `Bearer`；401 清 token 跳登录。

### Q40. 路由守卫做了什么？
**要点**：`beforeEach` 校验 `requiresAuth`（未登录跳登录）与 `admin`（非管理员跳首页），`guestOnly` 防止已登录重复进登录页。

### Q41. 跨域怎么解决的？生产环境呢？
**要点**：开发用 Vue devServer 代理 `/api`、`/uploads` 到 8080；后端配 CORS 仅放行 8081；生产把前端打包进后端 static，同源无跨域。

### Q42. 打包后刷新 /notes/1 为什么 404？怎么解决？
**要点**：history 路由需要服务端回退；`SpaForwardController` 把前端路由 forward 到 `index.html`，静态资源不受影响。

## G. 工程化与测试（Q43–Q45）

### Q43. 日志都记了什么？怎么避免泄露密码？
**要点**：登录/注册、上传、审核、下架、评论、AI 失败；只记 username/userId，不记密码与 token；异常日志不打敏感参数。

### Q44. 56 个接口用例覆盖了哪些风险？
**要点**：认证（401/403）、参数校验、上传、笔记 CRUD 与越权、审核全流程、点赞幂等、评论级联、关注、后台权限、AI 降级、404；报告在 `docs/api-test-report.md`。

### Q45. 如果 QPS 涨 100 倍，你怎么改？
**要点**：先定位瓶颈（慢 SQL/连接池/热点）；加 Redis 缓存公开流与计数、读写分离、分页深翻优化、接口限流、异步化（AI/通知）、水平扩容（无状态 JWT 友好）、静态资源 CDN。

## H. 开放题（加分）

### H1. 现场加一个"收藏"功能，你怎么设计？
**要点**：新表 `note_favorite(user_id,note_id,created_at)` + 唯一索引；4 个接口（收藏/取消/我的收藏/是否收藏）；详情返回 `favorited`；前端按钮 + 我的收藏页；补 6 个用例。

### H2. 你觉得项目最大的不足是什么？
**要点**（诚实 + 有改进方案）：无单元测试、JWT 无法主动失效、点赞计数弱一致、文件存本地、AI 同步调用无限流。

### H3. 如果重做一次，你会改变什么？
**要点**：先用 OpenAPI 定义接口再写代码；补 Service 单测；引入 Redis 做缓存与计数；密钥全部外置；加操作审计表。

### H4. 这个项目你独立完成了哪些部分？
**要点**：讲清楚自己负责的模块 + 能指出具体代码位置 + 能解释为什么这么写（避免泛泛而谈）。

### H5. 你从这个项目学到了什么？
**要点**：分层与边界、状态机思维、并发下的幂等与计数、AI 工程的降级与成本控制、测试驱动的联调。
